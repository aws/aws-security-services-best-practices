# 권장 WAF 규칙 순서

규칙 평가 순서는 AWS WAF protection pack을 구성할 때 가장 영향력 있는 결정 중 하나입니다. 규칙은 나타나는 순서대로 평가되며, [종료 작업](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-rule-actions.html)(*Allow* 및 *Block*)은 평가를 즉시 중지합니다. 규칙을 잘못된 순서로 배치하면 오탐, 미탐 또는 불필요한 비용이 발생할 수 있습니다. 이 섹션에서는 모든 일반적인 WAF 규칙 유형에 대한 권장 순서와 각 위치의 이유를 설명합니다.

## 종료 작업 이해

가장 중요한 개념 중 하나는 *Count* 이외의 작업이 [종료](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-rule-actions.html)될 수 있다는 것입니다. *Allow*와 *Block*은 항상 종료됩니다. 어느 작업으로든 규칙이 일치하면 더 이상 규칙이 평가되지 않습니다. *CAPTCHA*와 *Challenge*는 조건부 종료입니다. 클라이언트가 성공적으로 완료할 수 없는 경우에만 요청을 종료합니다. *Allow* 작업을 사용할 때, 특히 protection pack 상단 근처에서 주의하세요. *Allow* 작업이 있는 규칙은 후속 규칙이 차단했을 요청이라도 허용합니다.

protection pack이 종료 작업이 있는 규칙에서 일치하면, 그 이후의 규칙은 평가되지 않습니다. 이는:
    * 유료 규칙(Bot Control, Fraud, 3P 규칙)이 사용량 기반 비용을 발생시키지 않음
    * 해당 규칙의 레이블이 추가되지 않음. 이것은 WAF 로그 및 WAF 로그 필터링에 관련됩니다.

규칙 순서는 하나의 규칙에서 다른 규칙의 레이블을 사용할 때도 중요합니다. 레이블은 요청이 해당 규칙을 통과할 때만 추가됩니다. 예를 들어, AMR의 레이블을 사용하는 사용자 정의 규칙은 해당 AMR *이후*에 와야 합니다. 이것은 [오탐 처리](../../operationalizing/docs/index.md#creating-exceptions)에서 일반적입니다.

## 권장 규칙 평가 순서

protection pack의 기본 작업이 *Allow*라고 가정하면, protection pack 상단 근처에서 가능한 한 많은 원치 않는 요청을 차단하는 것이 합리적입니다. 가장 넓은 범위의 원치 않는 트래픽에 적용되는 규칙을 상단에 배치하세요. 좁은 기준이 있거나 요청당 요금이 있는 규칙을 끝에 배치하세요.

다음 표는 규칙 순서에 대한 더 자세한 권장 사항을 제공합니다.

| 우선순위 | 규칙 유형 | 작업 | 근거 |
|----------|-----------|--------|-----------|
|  1 | Shield Advanced Anti-DDoS AMR | 다양 | 레이어 7 DDoS 감지 및 완화 |
|  2 | IP 허용 목록 | Allow | Anti-DDoS AMR을 제외하고 절대 차단되어서는 안 되는 명시적 IP, 가급적 사용하지 않음 |
|  3 | IP 차단 목록 | Block | 차단해야 하는 명시적 IP. 사용자 정의 위협 인텔리전스에 일반적 |
|  4 | 지역 차단 규칙 | Block | 이 엔드포인트에 접근할 수 없어야 하는 국가 |
|  5 | 비율 기반 규칙(일괄) | Block | 일반적으로 클라이언트 IP 기반의 높은 기준 비율 제한 |
|  6 | 비율 기반 규칙(범위 지정) | Block | HTTP 메서드 범위 또는 고비용 URI를 포함하는 일반적인 예 |
|  7 | IP 평판/익명 규칙 | Block | 알려진 악성 또는 난독화된 소스(VPN, 클라우드 프로바이더)의 IP |
|  8 | AWS 관리형 기본 규칙(CRS, Known Bad Inputs) | Block | 모든 애플리케이션에 대한 광범위한 위협 커버리지 |
|  9 | AWS 관리형 사용 사례 규칙(SQL Database 등) | Block | 애플리케이션별 위협 커버리지 |
| 10 | 오탐 예외 및 애플리케이션별 규칙 | Block | 오탐 처리 또는 애플리케이션별 보호 |
| 11 | 파트너 관리형 규칙 | Block | 다양한 유형의 보호. 무료 사용 규칙 이후 배치하여 비용 절감. |
| 12 | Bot Control | Block/Challenge | 봇 트래픽 감지 및 관리(범위 축소 포함) |
| 13 | Fraud Control (ATP, ACFP) | Block | 로그인 및 계정 생성 페이지 보호(범위 축소 포함) |

## 순서의 근거

권장 순서는 일반 원칙을 따릅니다: **가장 적은 비용으로 가능한 한 빨리 가장 많은 트래픽을 차단합니다.**

- **Anti-DDoS가 먼저** 오는 이유는 애플리케이션 계층 DDoS 공격을 감지하고 완화하기 위해 모든 트래픽을 볼 필요가 있기 때문입니다. 먼저 배치하면 다른 규칙이 평가를 종료하기 전에 DDoS 완화가 적용됩니다. IP 허용 목록도 DDoS 탐지를 우회해서는 안 됩니다.
- **IP 허용/차단 목록이 다음** 인 이유는 명시적이고 저비용 결정이기 때문입니다. 허용된 IP는 모든 다운스트림 평가(및 비용)를 건너뛰고, 차단된 IP는 즉시 삭제됩니다. 허용 목록을 최소화하세요. 광범위한 IP 허용 목록이 역효과를 낼 수 있는 이유는 [사용자 정의 규칙](../../custom-rules/docs/index.md)을 참조하세요.
- **비율 기반 규칙(일괄 및 범위 지정)이 뒤따르는** 이유는 더 비싼 다운스트림 규칙에서 용량을 소비하기 전에 볼류메트릭 남용을 조기에 중지하기 때문입니다. 일괄 비율 제한은 광범위한 폭주를 포착하고, 범위 지정 비율 제한은 특정 고비용 또는 민감한 URI를 보호합니다.
- **지역 차단 규칙**은 애플리케이션에 접근할 합법적인 이유가 없는 지역의 트래픽을 제거합니다. IP 평판 전에 배치하면 어차피 지리에 의해 차단될 트래픽을 평가하는 데 사이클을 소비하지 않습니다.
- **IP 평판 및 익명 IP 규칙**은 알려진 악성 또는 난독화된 소스의 트래픽을 삭제합니다. 평가 비용이 낮고 콘텐츠 검사 규칙에 도달하는 요청 볼륨을 줄입니다.
- **무료 AWS 관리형 규칙(CRS, Known Bad Inputs, 사용 사례 규칙)**은 광범위하고 애플리케이션별 위협 커버리지를 제공합니다. 비율 제한, 지역 차단, IP 평판을 통과한 트래픽이 합법적일 가능성이 높지만 콘텐츠 검사가 여전히 필요하므로 중간에 위치합니다.
- **오탐 예외 및 애플리케이션별 규칙**은 관리형 규칙 이후에 오는 이유는 해당 관리형 규칙이 생성한 레이블에 의존하기 때문입니다. 이러한 규칙은 알려진 오탐 패턴에 대한 예외와 함께 차단을 다시 구현합니다.
- **파트너 관리형 규칙**은 무료 규칙 이후에 배치하여 요청당 비용을 줄입니다. 업스트림 규칙에 의해 이미 차단된 트래픽은 파트너 규칙 평가에 도달하지 않습니다.
- **Bot Control 및 Fraud Control이 마지막**인 이유는 요청당 요금이 가장 높기 때문입니다. 다른 모든 규칙 이후에 배치하면 다른 모든 필터를 통과한 트래픽만 평가되어 비용을 최소화합니다. 범위 축소 문은 이러한 규칙 그룹이 검사하는 요청을 더욱 제한합니다.

## 순서가 달라질 수 있는 시나리오

위의 권장 순서는 대부분의 웹 애플리케이션에 적합합니다. 그러나 특정 애플리케이션 프로필은 조정이 유리할 수 있습니다.

### 대량 API 트래픽 vs. 정적 콘텐츠 사이트

주로 API 트래픽을 제공하는 애플리케이션은 사용자 정의 검증 규칙(예: 필수 API 키, 예상 콘텐츠 유형)을 평가 순서에서 더 높이 배치하는 것이 유리할 수 있습니다. 정적 콘텐츠 사이트는 사용 사례별 관리형 규칙이 전혀 필요하지 않을 수 있습니다.

### 엄격한 지리적 제한이 필요한 애플리케이션

애플리케이션이 특정 지역에 엄격히 제한되는 경우, IP 평판 규칙 위에 지리 기반 규칙을 이동하는 것을 고려하세요. 이렇게 하면 허용되지 않는 지역의 트래픽이 다른 평가 전에 차단됩니다.

## 비율 기반 규칙

WAF [비율 기반 규칙](https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-type-rate-based.html)은 최대 10,000개의 소스 IP(비율 기반 규칙당)에서 요청을 카운트하고, 클라이언트가 후행 5분 기간에 걸쳐 측정된 임계값을 초과하면 요청을 차단합니다. 이것은 AWS WAF에서 종종 간과되는 기능이지만, protection pack에 추가할 수 있는 가장 간단하고 가치 있는 규칙 중 하나입니다. 대부분의 고객은 모든 protection pack에 최소 하나의 비율 기반 규칙이 있어야 합니다.

비율 기반 규칙을 활용하는 방법에 대한 전체 설명은 블로그 [가장 중요한 세 가지 AWS WAF 비율 기반 규칙](https://aws.amazon.com/blogs/security/three-most-important-aws-waf-rate-based-rules/)을 참조하세요. 요약하면, 가장 중요한 세 가지 비율 기반 규칙은:

1. 모든 요청에 적용되는 **일괄 비율 기반 규칙**. 이것은 위의 평가 순서에서 위치 1에 권장되는 규칙입니다.
2. 더 제한적인 제한으로 애플리케이션의 특정 부분을 보호하는 **URI별 비율 기반 규칙**. 이것은 위의 평가 순서에서 위치 8에 권장되는 규칙입니다.
3. 다른 규칙이나 위협 인텔리전스에 의해 이미 악성으로 식별된 IP의 요청 비율을 제한하는 **알려진 악성 소스 IP에 대한 비율 기반 규칙**.
