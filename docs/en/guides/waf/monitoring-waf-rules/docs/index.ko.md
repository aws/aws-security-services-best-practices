# WAF 로그 쿼리 및 시각화

이 가이드 섹션은 각 접근 방식의 *이유*를 설명하여 정보에 입각한 결정을 내릴 수 있도록 하는 데 중점을 둡니다. 배경 맥락 없이 따를 수 있는 명확한 경로만 필요한 경우 전체적으로 실용적인 권장 사항을 제공합니다. 많은 경우 관찰 가능성에 대한 확립된 접근 방식이 이미 있으며, 이 가이드는 해당 시스템을 운영하고 WAF 로그 데이터를 소비하는 방법을 이해하는 데 도움을 줄 것입니다.

**효과적인 WAF 모니터링에는 두 가지가 필요합니다:**

로그를 쿼리하는 기능과 대시보드를 통해 추세를 시각화하는 기능. 네이티브 AWS WAF 대시보드는 빠른 운영 뷰를 제공하며 CloudWatch Logs가 로그 대상인 소규모 팀 또는 단일 애플리케이션 배포에 적합합니다. CloudWatch Logs를 사용하지 않거나 소수 이상의 애플리케이션으로 작업하는 고객의 경우, WAF 로그를 기존 관찰 가능성 플랫폼으로 보내거나 AWS 네이티브 서비스를 사용하여 WAF 로그 데이터를 쿼리하고 시각화할 수 있습니다. 일반적으로 WAF 모니터링을 팀이 이미 관찰 가능성에 사용하는 것과 일치시키세요.

이 가이드의 후반부는 쿼리를 통해 로그에서 가치를 얻는 데 중점을 둡니다. 중첩된 규칙 그룹 평가, 레이블, 요청 헤더, 종료 규칙 세부 정보를 포함한 WAF 로그 필드를 완전히 구문 분석하는 포괄적인 "슈퍼 쿼리"부터 시작합니다. 이러한 쿼리는 필요하지 않은 부분을 주석 해제하고 삭제하여 구축할 수 있는 견고한 시작점으로 설계되었습니다. 거기서부터 일반적인 운영 사용 사례에 대한 집중 쿼리를 다룹니다: Count에서 Block으로 전환하기 전에 AWS 관리형 규칙 영향 평가, 비율 기반 규칙에 대한 적절한 임계값 결정, 잘 설계된 오탐 예외의 범위를 지정하기 위한 패턴 식별.

## 포괄적인 시작 쿼리

이 섹션의 쿼리는 의도적으로 크고 포괄적입니다. 목표는 필요하지 않은 것을 주석 해제하고 삭제하여 대부분의 쿼리를 구축할 수 있는 템플릿을 제공하는 것입니다. WAF 로그에서 값을 추출하는 구문 분석 및 SQL 로직과 카운트 방법과 같은 일반적인 작업의 여러 예가 이미 완료되어 있으므로 쿼리 자체를 작성하는 방법이 아닌 필요한 것에 집중할 수 있습니다.

이러한 쿼리의 많은 열은 AWS 관리형 규칙(AMR) 레이블을 구문 분석합니다. 레이블은 해당 관리형 규칙 그룹이 protection pack에 연결되어 *있고* 규칙이 요청을 평가한 경우에만 로그 레코드에 존재합니다. 예를 들어, protection pack에 Bot Control(Common)이 없으면 `verified`/`unverified` 레이블이 나타나지 않으며 해당 열은 null을 반환합니다.

전체 Athena 및 CloudWatch Log Insights 쿼리는 이 페이지의 영어 버전을 참조하세요. 쿼리는 SQL/쿼리 언어이므로 번역이 필요하지 않습니다.

### Athena

포괄적인 Athena 쿼리 템플릿은 영어 버전의 이 페이지를 참조하세요. 쿼리는 다음을 포함합니다:

- 로그 시간, 클라이언트 IP, 국가, 작업, 종료 규칙 등 기본 필드
- 호스트, User-Agent, URI 등 요청 헤더 추출
- 토큰 상태, Amazon IP 목록, 익명 IP 목록 등 AMR 레이블 구문 분석
- Bot Control 레이블(카테고리, 이름, 검증 상태)
- 도메인 카테고리 레이블
- 규칙 그룹 평가 세부 정보

### Amazon CloudWatch Log Analytics

포괄적인 CloudWatch Log Insights 쿼리 템플릿은 영어 버전의 이 페이지를 참조하세요.

## WAF 로그 쿼리를 통한 AWS WAF 규칙 평가

### 비율 기반 규칙: 적절한 임계값 식별

비율 기반 규칙의 올바른 임계값을 설정하려면 정상 트래픽에서 가장 높은 합법적 요청 비율이 무엇인지 이해해야 합니다. 다음 쿼리는 5분 기간(WAF 비율 기반 규칙의 기본 평가 기간)별로 소스 IP당 요청 수를 보여줍니다.

#### 일반: 소스 IP당 요청

이것은 가장 기본적인 비율 기반 규칙 분석입니다. 5분 기간 동안 단일 소스 IP에서 얼마나 많은 요청이 오는지를 보여줍니다.

**결과 읽는 방법:** 상위 결과에서 가장 높은 request_count를 찾습니다. 이것이 현재 최대 합법적 비율입니다. 시작 임계값으로 이보다 50-100% 높게 설정하세요. 예를 들어, 가장 높은 합법적 IP가 5분에 500개 요청을 보내면 750-1,000의 임계값으로 시작하세요.

Athena 및 CloudWatch Log Insights 쿼리는 영어 버전의 이 페이지를 참조하세요.

#### 복합 키: 소스 IP + 쿠키

여러 사용자가 동일한 IP를 공유할 때(기업 NAT, 공유 프록시) 사용합니다. 쿠키를 추가하면 동일한 IP 뒤의 개별 클라이언트를 구별할 수 있습니다.

#### 복합 키: 소스 IP + Protection Pack ARN

여러 리소스가 동일한 protection pack을 공유할 때 사용합니다. 특정 리소스에 대한 비율 기반 규칙의 영향을 이해하는 데 도움이 됩니다.

#### 복합 키: 소스 IP + 호스트 이름

여러 호스트 이름이 동일한 protection pack 뒤에 있을 때 사용합니다.

### Count에서 Block으로 전환하기 전에 AWS 관리형 규칙 평가

관리형 규칙을 Count 모드에서 Block 모드로 전환하기 전에, 규칙이 트래픽에 대해 어떻게 매칭하는지 이해하는 것이 중요합니다. 다음 쿼리는 어떤 규칙이 트리거되고 있는지, 어떤 엔드포인트에서, 얼마나 자주 트리거되는지 보여줍니다.

#### 엔드포인트, URI, HTTP 메서드별 규칙 그룹 일치 카운트

이 쿼리는 관리형 규칙 그룹 매칭을 호스트 이름, URI 경로, HTTP 메서드별로 집계합니다. 이를 통해 어떤 엔드포인트와 요청 유형이 가장 많이 매칭되는지 볼 수 있어 오탐이 발생할 가능성이 가장 높은 곳에 대한 조사를 집중할 수 있습니다.

#### 특정 규칙 레이블과 일치하는 개별 요청

특정 규칙에서 매칭을 발견한 후, 실제 요청을 검사하여 합법적 트래픽인지(오탐) 실제 공격인지 확인해야 합니다.

**결과 읽는 방법:** 각 행을 검사하여 요청이 합법적인지 결정합니다. 주의해야 할 핵심 필드: `uri`(요청이 예상 엔드포인트를 대상으로 하는가?), `httpMethod`(메서드가 엔드포인트에 적합한가?), `userAgent`(사용자 에이전트가 합법적인 클라이언트 소프트웨어처럼 보이는가?).

#### 보조 신호 필터링과 함께 규칙 레이블과 일치하는 요청(오탐 가능성)

이 쿼리 변형은 IP 평판 레이블 또는 익명 IP 레이블과 같은 보조 신호를 추가하여 잠재적 오탐에 대한 조사를 집중합니다. IP 평판 레이블이 없는 소스에서 매칭이 발생하면 오탐일 가능성이 더 높습니다.

모든 쿼리의 전체 SQL/CloudWatch 구문은 이 페이지의 영어 버전을 참조하세요.
