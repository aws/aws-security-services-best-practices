# WAF 로깅

AWS WAF는 검사하는 모든 요청을 기록할 수 있으며, 수행된 작업, 일치한 규칙, 적용된 레이블, 헤더, 쿼리 문자열, 소스 IP 등의 요청 세부 정보를 캡처합니다. 이러한 로그는 규칙이 의도한 대로 작동하는지 검증하고, 보안 인시던트를 조사하고, 오탐을 줄이기 위해 규칙을 조정하고, 시간에 따른 트래픽 패턴을 이해하는 데 필수적입니다. WAF 로그 없이는 요청이 왜 차단되었는지 또는 허용되었는지 확인할 수 없으며, 새로 공개된 취약점에 의해 애플리케이션이 대상이 되었는지 소급하여 확인할 수도 없습니다.

AWS WAF는 비용, 쿼리 성능, 네이티브 ETL 기능, 운영 복잡성을 포함한 다양한 이점을 가진 여러 [전달 메커니즘 및 저장 대상](#적합한-로깅-접근-방식)을 지원합니다. 이 페이지에서는 사용 가능한 [네이티브 AWS 로그 대상](#로그-대상)과 저장 위치에 따른 [로그 쿼리](#s3에-저장된-로그에-대한-고려-사항) 방법을 안내합니다. [로그 보존](#로그-보존) 요구 사항도 결정해야 합니다. 운영 사용 사례, 규정 준수 의무 또는 인시던트 대응 조회 기간에 따라 이 데이터가 얼마나 오래 필요한지 식별하고, 비즈니스 또는 보안 가치를 제공하지 않는 트래픽을 제외하여 볼륨을 줄이기 위해 [로그 필터링](#로그-필터링)을 적용할지 결정하세요.

## 로그 대상

AWS WAF 로그는 Amazon CloudWatch Logs, Amazon S3, Amazon OpenSearch Serverless 또는 타사 대상으로 보낼 수 있습니다. 각 옵션에 대한 전체 세부 사항은 [AWS WAF 로깅 대상](https://docs.aws.amazon.com/waf/latest/developerguide/logging.html)을 참조하세요.

| 차원 | CloudWatch 로그 그룹 | Amazon S3 | OpenSearch Serverless | 타사(Splunk, Datadog 등) |
|---|---|---|---|---|
| **전달 방법** | CloudWatch Vended Logs | Firehose 또는 CloudWatch Vended Logs | Firehose | Firehose |
| **저장 비용** | $0.03/GB/월 | $0.023/GB/월(Standard); $0.004/GB/월(Glacier) | $0.30/GB/월(Managed Storage - Hot) | 플랫폼에 따라 다름 |
| **쿼리 비용** | $5/TB 스캔(Logs Insights) | $5/TB 스캔(Athena) | OCU 검색 용량에 포함 | 타사 라이센스에 포함 |
| **쿼리 도구** | CloudWatch Logs Insights | Amazon Athena(SQL) | OpenSearch Dashboards / 쿼리 DSL / SQL | 플랫폼 네이티브 |
| **내장 대시보드** | 네이티브 AWS WAF 대시보드 | 없음(QuickSight 추가) | OpenSearch Dashboards(포함) | 플랫폼 네이티브 |
| **교차 계정 전달** | 지원되지 않음 | 예 | 예(Firehose 통해) | 예(Firehose 통해) |
| **교차 리전 전달** | 지원되지 않음 | 예 | 예(Firehose 통해) | 예(Firehose 통해) |
| **Firewall Manager 지원** | 로그 대상으로 지원되지 않음 | 예 | 예(Firehose 통해) | 예(Firehose 통해) |
| **적합한 용도** | 빠른 설정; 네이티브 WAF 대시보드; 중간 로그 볼륨 | 비용 효율적인 장기 저장; 대량; 임시 쿼리 | 실시간 대시보드; 전체 텍스트 검색; 빈번한 조사 | 기존 SIEM/관찰 가능성 플랫폼 |

## 로그 전달

AWS WAF는 두 가지 전달 메커니즘을 지원합니다. 선택하는 전달 메커니즘에 따라 선택할 수 있는 저장 대상, 로그가 저장 대상에 도달하는 속도, 전송 중 사용 가능한 기능 및 전달 비용이 결정됩니다.

| 차원 | CloudWatch Vended Logs | Amazon Data Firehose |
|---|---|---|
| **전달 빈도** | 최대 5분마다 | 60초부터 구성 가능(최선의 노력/버퍼 힌트) * |
| **첫 인사이트까지 시간** ** | 요청 검사 후 ~5분 | 요청 검사 후 60초(최선의 노력/버퍼 힌트) * |
| **전달 비용** | $0.50/GB vended 로그 전달 요금(S3); 수집 요금 적용(CloudWatch Logs) | $0.029/GB, 5KB 최소 레코드 크기, 실질적으로 백만 WAF 로그 레코드당 $0.145 |
| **지원되는 저장 대상** | CloudWatch Logs, Amazon S3 | Amazon S3, OpenSearch Serverless, 타사(Splunk, Datadog 등) |
| **교차 계정 전달** | 예(S3); 지원되지 않음(CloudWatch Logs) | 예 |
| **교차 리전 전달** | 예(S3); 지원되지 않음(CloudWatch Logs) | 예 |
| **Firewall Manager 지원** | 예(S3); 지원되지 않음(CloudWatch Logs) | 예 |
| **ETL/변환** | 없음 | Lambda를 통한 레코드 변환, 형식 변환, 동적 파티셔닝 |
| **S3 접두사 제어** | 고정 분당 구조 | 완전 사용자 정의(권장: 시간별) |

\* Amazon Data Firehose는 버퍼 힌트 구성을 허용합니다. 이것은 원하는 전달 빈도/전달 전 최대 버퍼이지만 최선의 노력으로 사용되며 모든 경우에 발생하지 않을 수 있습니다.
\*\* 첫 인사이트까지 시간은 WAF가 요청을 검사하는 시점부터 해당 로그 레코드를 로깅 대상에서 쿼리할 수 있을 때까지의 시간을 의미합니다.

WAF 로그를 S3에 보내고 Athena로 쿼리하는 경우, 선택하는 S3 접두사 구조 및 Athena 파티셔닝 전략이 쿼리 성능과 비용에 직접적인 영향을 미칩니다. 자세한 지침은 [S3에서의 효과적인 로그 쿼리](#s3에서의-효과적인-로그-쿼리)를 참조하세요.

## 로그 보존

로그를 더 오래 보존할 비즈니스 또는 규정 준수 이유가 없다면, WAF 로그 사용 방법에 대한 조회 기간만 포함하도록 로그 보존을 구성하세요. 명시적 규정 준수 요구 사항이 없는 많은 고객의 경우, 30일 또는 90일이면 적극적인 조사를 지원하기에 충분합니다.

- **CloudWatch Logs** - 로그 그룹에 보존 기간을 설정합니다(예: 30, 60 또는 90일). 보존 기간보다 오래된 로그는 자동으로 삭제됩니다.
- **Amazon S3** - [S3 수명 주기 정책](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html)을 사용하여 로그를 더 저렴한 스토리지 클래스로 전환하거나 정의된 기간 후에 만료합니다.
- **Amazon OpenSearch Serverless** - 시계열 컬렉션에 [데이터 수명 주기 정책](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-lifecycle.html)을 구성하여 보존 기간보다 오래된 인덱스를 자동으로 삭제합니다.
- **타사 대상** - 보존은 타사 플랫폼 내에서 자체 정책 및 라이센스에 따라 관리됩니다.

## 필드 편집

민감한 데이터를 포함할 수 있는 필드를 기록하지 않으려면, [AWS WAF 로그에서 필드를 편집](https://docs.aws.amazon.com/waf/latest/developerguide/logging-management.html)할 수 있습니다. AWS WAF 로그에는 BODY가 포함되지 않습니다. 그러나 특정 유형의 Amazon 관리형 규칙은 규칙과 일치하는 본문 부분을 포함합니다.

편집할 일반적인 헤더에는 `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-API-Key`, `X-Amz-Security-Token`이 포함됩니다. 이것은 예시일 뿐입니다. 애플리케이션이 민감한 정보를 포함하는 다른 헤더나 쿼리 문자열과 같은 다른 요청 속성을 사용할 수 있습니다. 애플리케이션이 보내고 받는 것을 검토하여 WAF 로그에 나타나지 않아야 하는 것을 결정하세요.

편집은 영구적입니다. 필드가 편집되면 해당 값은 로그에 기록되지 않으며 검색할 수 없습니다. 나중에 조사를 위해 해당 데이터가 필요한 경우 사용할 수 없습니다.

## 로그 필터링

AWS WAF를 사용하면 로깅 대상에 보내는 요청을 필터링할 수 있습니다. 이것은 거의 항상 비용 제어로 사용됩니다. 일부 트래픽은 로깅 비용을 정당화할 비즈니스 가치가 없을 수 있으며 건너뛸 수 있습니다. 보편적인 정답은 없습니다. 아래는 고객이 캡처하거나 캡처하지 않는 일반적인 예입니다:

* 보안 팀이 보안 인시던트가 소급적으로 발생했는지 검증할 수 있어야 합니다. 허용된 트래픽만 기록합니다. 요청이 차단된 경우, 보안 측면에서 요청이 알려지지 않았거나 감지되지 않은 방식으로 애플리케이션을 익스플로잇한 위험은 없습니다.

* 고객 기반이 지리적으로 집중/제한됩니다. *차단하지 않을 국가 목록* 또는 *차단할 특정 국가 목록*에 의해 차단된 요청을 기록합니다. 이를 적용하는 사용자 정의 규칙은 사용자 정의 레이블을 내보내고 이를 필터링하여 기록하지 않을 수 있습니다.

* 높은 신뢰도 규칙, 특히 DDoS 맥락에서. DDoS 이벤트는 대량의 트래픽을 생성하며, 경우에 따라 정상적으로 경험하는 것보다 수백, 수천, 수백만 배 이상 더 많은 트래픽이 될 수 있습니다. 로깅의 맥락에서, 로그 필터링 없이는 이것은 해당하는 WAF 로깅 비용 급증을 의미합니다. `awswaf:managed:aws:anti-ddos:low-suspicion-ddos-request` 또는 `awswaf:managed:aws:amazon-ip-list:AWSManagedIPDDoSList`와 같은 높은 신뢰도 레이블을 사용하면 대부분의 경우 DDoS 급증의 전부 또는 대부분이 기록되지 않도록 제거할 수 있습니다.

**WAF 로그 필터링을 활성화하지 않는 이유**
특정 요청에 대한 WAF 로그 없이는, WAF 작업이 수행된(또는 수행되지 않은) 이유, 쿼리 문자열, 헤더 등의 요청 속성을 신뢰성 있게 식별할 수 없습니다.

## 적합한 로깅 접근 방식

### 빠른 선택

| 대상 | 적합한 사용 사례 |
|---|---|
| **CloudWatch Logs** | 네이티브 WAF 대시보드와 함께 AWS WAF로 가장 간단하게 설정하고 사용을 시작. 단일 애플리케이션/엔드포인트 사용 사례에 적합. |
| **Amazon S3 + Athena** | 가장 낮은 보존 비용; 규정 준수 또는 감사 요구 사항과 같은 장기 보존에 탁월; 더 긴 실행 시간을 허용할 수 있는 임시 쿼리(인시던트 조사, 정기 검토); 이미 S3 기반 데이터 레이크 전략이 있는 경우. 대시보드 생성에는 추가 서비스(예: QuickSight)가 필요. |
| **OpenSearch/OpenSearch Serverless** | 대규모에서도 Athena보다 훨씬 빠른 쿼리 시간의 네이티브 대시보드 기능(대시보드는 구축해야 함); 빈번한 조사를 수행하는 보안 팀; 쿼리 빈도가 OCU 기준 비용을 정당화하는 중간에서 높은 로그 볼륨. |
| **타사(Splunk, Datadog 등)** | 조직에 이미 중앙 집중식 SIEM/관찰 가능성 플랫폼이 있는 경우; WAF 로그를 애플리케이션 로그, 인프라 지표 및 기타 보안 데이터와 하나의 도구에서 상관관계를 분석해야 하는 경우. |

### 권장 사항

WAF 로그를 어떻게 사용할 계획인지 고려하는 것부터 시작하세요. WAF 로그 데이터를 적극적으로 조사할 계획이고(인시던트 대응, 규칙 조정, 트래픽 분석) 조직이 이미 중앙 집중식 SIEM 또는 관찰 가능성 플랫폼(Splunk, Datadog, OpenSearch 등)을 운영하고 있다면, Firehose를 통해 WAF 로그를 거기에 전달하세요. 팀에 이미 워크플로, 대시보드, 알림이 갖춰져 있으므로 도구를 중복하지 말고 이미 알고 있는 것을 사용하세요.

소규모 팀이나 WAF를 사용하는 개별 애플리케이션의 경우, 네이티브 AWS WAF 대시보드와 함께 **CloudWatch Logs**를 사용하세요. 추가 설정 없이 즉각적인 가시성을 제공하며 주로 규칙 동작을 검증하고 최근 트래픽을 문제 해결해야 할 때 충분합니다.

중앙 집중식 또는 조직 전체 WAF 로그 수집의 경우, **Amazon S3**와 **OpenSearch Serverless** 간의 AWS 네이티브 선택은 데이터를 어떻게 소비할 계획인지에 따라 다릅니다. 사용 사례가 주기적 임시 쿼리(인시던트 조사, 규정 준수 감사, 규칙 영향 검토)인 경우 S3 + Athena가 보관 시 가장 낮은 비용을 제공하고 모든 볼륨으로 확장됩니다. 사용 사례가 운영적(빈번한 대화형 쿼리, 실시간 대시보드, WAF 패턴에 대한 알림)인 경우 OpenSearch Serverless가 추가 서비스(Athena + QuickSight)를 결합하지 않고도 이를 지원하는 쿼리 성능과 내장 시각화를 제공합니다.

어떤 대상을 선택하든:

- **[로그 보존](#로그-보존)** - 규정 준수 요구 사항이나 사용 사례에 데이터가 필요한 기간(인시던트 조사 조회, 규칙 조정 검증)에 따라 보존을 설정하세요. 특정 요구 사항이 없으면 30일이 좋은 최소값입니다.
- **[필드 편집](#필드-편집)** - 민감한 데이터(자격 증명, 토큰, API 키)가 포함된 헤더나 요청 속성을 편집하세요.
- **[로그 필터링](#로그-필터링)** - 많은 고객이 WAF 로그를 필터링하지 않습니다. 사용 사례에 따라 비즈니스 또는 보안 가치를 제공하지 않는 트래픽을 필터링하여 로그 볼륨과 비용을 줄이는 것을 고려하세요.

## S3에 저장된 로그에 대한 고려 사항

### S3 접두사 구조

CloudWatch Vended Logs와 Amazon Data Firehose는 다른 S3 접두사 구조를 사용하여 WAF 로그를 기록합니다. Amazon Data Firehose는 구조를 사용자 정의할 수 있지만 CloudWatch Vended Logs는 그렇지 않습니다. 이러한 접두사 패턴은 Amazon Athena가 데이터를 파티셔닝하고 쿼리하는 방식에 직접 영향을 미칩니다.

CloudWatch Vended Logs는 고정 **분당** 접두사 구조로 기록합니다:

```
AWSLogs/{AccountId}/WAFLogs/{Scope}/{WebAclName}/{YYYY}/{MM}/{dd}/{HH}/{mm}/log_file.log.gz
```

이 접두사 구조는 AWS WAF 서비스에 의해 설정되며 변경할 수 없습니다.

Amazon Data Firehose는 S3 접두사에 대한 제어를 제공합니다. **시간별** 세분성을 구성하면 동일한 시간 범위에 대해 60배 적은 파티션 경로를 생성합니다:

```
{BucketPrefix}/{YYYY}/{MM}/{dd}/{HH}/log_file.log.gz
```

트레이드오프는 1시간 미만으로 범위가 지정된 쿼리가 여전히 전체 시간의 데이터를 스캔한다는 것입니다. 쿼리 패턴 및 파티셔닝 전략에 따라 이 세분성 차이가 쿼리 성능에 의미 있는 영향을 미칠 수 있습니다([S3에서의 효과적인 로그 쿼리](#s3에서의-효과적인-로그-쿼리) 참조).

### S3에서의 효과적인 로그 쿼리

Amazon Athena를 사용하여 S3에 저장된 WAF 로그를 쿼리할 때, 쿼리 성능은 Athena 테이블이 어떻게 파티셔닝되어 있는지에 따라 다릅니다. 아래 예는 하루 10GB의 로그를 생성하는 WAF 배포와 세 가지 일반적인 쿼리를 가정합니다:

```sql
-- 단일 일
SELECT * FROM waf_logs
WHERE log_time >= '2026/06/25/00/00' AND log_time < '2026/06/26/00/00'

-- 특정 5분 기간
SELECT * FROM waf_logs
WHERE log_time >= '2026/06/25/14/30' AND log_time < '2026/06/25/14/35'

-- 최근 30일
SELECT * FROM waf_logs
WHERE log_time >= '2026/05/25/00/00' AND log_time < '2026/06/26/00/00'
```

**파티션 없음**

파티션 없이 Athena는 `WHERE` 절에 관계없이 매번 쿼리할 때 테이블의 모든 데이터를 스캔합니다. 이것은 의미 있는 규모에서의 비용과 시간 영향으로 인해 WAF 로그에 권장되지 않습니다.

**권장: 파티션 프로젝션**

테이블 생성 시 Athena에 데이터가 존재할 수 있는 위치를 계산하는 방법을 알려주는 파티션을 정의합니다. Athena는 관련 날짜/시간의 데이터만 확인하고 스캔하여 파티션 없는 것보다 비용 효율적입니다. 트레이드오프는 Athena가 스캔을 시작하기 전에 범위 내 파티션당 S3 LIST 호출을 통해 각 파티션 경로를 확인하는 사전 작업을 수행해야 한다는 것입니다. 대규모(수천 개의 파티션)에서 이것은 각 쿼리 시작 전에 의미 있는 시간을 추가할 수 있지만, 실제로 스캔된 데이터에 대해서만 비용을 지불합니다.

**권장: 카탈로그 기반 파티션(Glue Crawler)**

AWS Glue Crawler를 구성하여 Glue Data Catalog에서 파티션을 자동으로 검색하고 등록합니다. Athena는 범위 내 파티션당 S3 LIST API 호출을 발행하는 대신 카탈로그를 직접 쿼리하여 일치하는 파티션을 찾습니다. 이는 쿼리 시 거의 모든 사전 작업을 제거합니다. 초기 Crawler 설정이 필요하고 실행당 작은 비용이 있지만, 한 번 구성하면 지속적인 유지 관리가 없는 관리형 서비스입니다. WAF 로깅 맥락에서의 Glue Crawler 비용 세부 사항은 [WAF 비용](../../waf-cost/docs/index.md)을 참조하세요.

**S3 쿼리 요약**

항상 쿼리에 날짜/시간 범위를 사용하세요. CloudWatch Log Insights와 Athena 모두 스캔된 데이터를 기반으로 청구합니다($5/TB 스캔). 필요한 만큼만 로그를 유지하세요.

CloudWatch Vended Logs를 사용하여 WAF 로그를 S3에 보내는 경우:
- Glue Crawler가 권장됩니다. WAF 로깅 비용 추정에 1% 미만의 비용 영향으로 일회성 설정이며 총 쿼리 실행 시간을 크게 줄일 수 있습니다.
- WAF 로그를 거의 쿼리하지 않을 것으로 예상되는 경우 파티션 프로젝션이 허용될 수 있습니다. 트레이드오프는 쿼리가 더 많은 파티션에 도달하여 전체 쿼리 시간이 길어질 수 있다는 것입니다.

Amazon Data Firehose를 사용하여 WAF 로그를 S3에 보내는 경우:
- Glue Crawler를 사용하면 분당 세분성이 스캔 비용이나 쿼리당 사전 작업 시간에 의미 있는 영향을 미치지 않습니다.
- Glue Crawler를 사용하지 **않으면** 시간별 세분성이 쿼리 실행당 사전 작업을 1/60로 줄입니다.
- Firehose는 60초마다 데이터를 보내도록 구성할 수 있으며(버퍼 힌트), 새 WAF 로그가 약 1분 안에 나타납니다.

Amazon Data Firehose의 특정 기능(버퍼 전달 시간, ETL)이 필요하지 않다면, 가장 비용 효율적인 전달 메커니즘을 사용하세요. CloudWatch Vended Logs인 경우 쿼리가 성능이 좋도록 Glue Crawler를 설정하세요. Amazon Data Firehose를 사용하는 경우 시간별 접두사로 S3에 로그를 기록하거나 Glue Crawler도 생성하세요.
